# 个人网站开源推广计划

本文面向愿意自行部署、持续打磨个人网站的开发者和数字花园爱好者。推广的目标是让真正需要的人理解项目、成功部署，并把真实问题带回仓库；不以短期曝光替代产品质量。

## 发布前清单

### 仓库与首发页

- [ ] 完善 GitHub README：用一句话说明网站适用人群、核心能力和技术栈，并放置清晰的在线预览、部署文档和问题反馈入口。
- [ ] 提供 3～5 张真实页面截图或短 GIF，展示首页、内容管理和移动端；图片应脱敏，不展示个人隐私数据。
- [ ] 补齐开源许可证、贡献指南、行为准则和安全策略，明确欢迎的贡献类型与反馈渠道。
- [ ] 为首个 Release 编写变更说明：新增能力、已知限制、升级或迁移注意事项，以及下一阶段计划。
- [ ] 设置 GitHub Topics、仓库描述和社交预览图；首发后置顶一条 Issue/Discussion，收集「部署结果、环境、报错和改进建议」。
- [ ] 从全新账号或干净环境完整跑一遍安装、配置和部署流程，确保文档中的命令可复制执行。

### 演示与安全边界

- [ ] 演示站使用无敏感数据的独立内容，并在页面或说明中标注其用途和维护范围。
- [ ] 当前 Cloudflare Worker 的写接口**未鉴权**。在完成鉴权、权限控制和必要的限流前，不要把管理或写入接口暴露到不受信任的公网，也不要在推广教程中鼓励读者这样部署。
- [ ] 部署教程应优先讲静态公开站点的安全发布；若需要演示写入能力，只在本地、受访问控制的测试环境，或完成安全加固后进行。

### 可量化的发布基线

发布当天记录以下基线，后续每周同一时间复盘：

| 指标 | 首月目标 | 记录方式 |
| --- | ---: | --- |
| GitHub Star | 50～150 | Insights / 仓库页面 |
| Fork | 10～30 | Insights / 仓库页面 |
| 有效部署反馈 | 10 条以上 | Issue、Discussion、表单汇总 |
| 主动反馈样本部署成功率 | 80% 以上 | 在反馈模板中明确填写成功/失败结果的成功样本数 ÷ 全部主动反馈样本数；不外推为所有访问者的成功率 |
| 首次响应时间 | 中位数与 90 分位均在 48 个自然小时内 | 从 Issue/Discussion 首次提交到维护者首次有效回复的时长；每周用全部新反馈计算中位数和 90 分位 |
| 内容链接访问转化 | 5% 以上 | 统一事件为「仓库落地页访问」；带 UTM 的内容链接点击后产生的落地页访问数 ÷ 该内容链接点击数 |

「有效部署反馈」必须包含至少环境、结果和一个可复现的观察；不要把简单点赞或无内容评论计入成果。

## 四周推广节奏

### 第 1 周：GitHub 首发与部署闭环

目标是让读者能在一次阅读内判断是否适合自己，并完成第一次部署。

- 在 GitHub 发布 Release，并同步一篇简短公告：项目解决什么问题、适合谁、三步启动路径和已知限制。
- 发布《从 Fork 到上线：部署这个个人网站的完整教程》，包含前置条件、环境变量说明、常见失败原因、回滚方式和安全提醒。
- 在 README、Release、教程结尾都指向同一份反馈模板，优先收集部署成功/失败案例。
- 指标：README 访问到部署文档的点击率、首周 5 条有效部署反馈、至少 3 个可复现的部署环境样本。

### 第 2 周：技术拆解，按平台重写而非简单搬运

目标是让不同平台的读者分别获得适合的技术信息，并回流到项目文档。

- **掘金**：发布 1 篇技术拆解，围绕 React + TypeScript、内容数据组织、国际化或部署链路中的一个具体问题，给出取舍、关键代码片段和仓库链接。避免把文章写成纯功能罗列。
- **知乎**：以问答或长文解释「个人网站是否值得自己维护」「静态站与可编辑站如何取舍」；用项目的实际设计决策作例子，透明说明限制和维护成本。
- **Bilibili**：制作 6～10 分钟录屏，演示从克隆、配置到本地运行和部署验证。镜头中说明写接口未鉴权的限制，不展示或引导公开暴露管理接口。
- **小红书**：做 6～8 页图文卡片，主题聚焦「一周搭好可自己维护的个人主页」或「个人网站部署避坑清单」；每页只讲一个动作，仓库链接放在简介或置顶说明中。
- 指标：每个平台各至少 1 条内容；按「带 UTM 的内容链接点击后产生的仓库落地页访问数 ÷ 该内容链接点击数」统计的访问转化率 5% 以上；收集 5 条能用于改进文档的具体问题。

### 第 3 周：公开真实迭代

目标是用可验证的改进建立信任，而不是追逐一次性流量。

- 汇总前两周的部署反馈，按「文档缺失、配置困惑、功能建议、缺陷」分类，公开一个简短迭代看板或 GitHub Discussion。
- 发布一次真实版本更新：说明收到的反馈、实际改了什么、未改的需求及原因；关联相关 Issue，感谢贡献者但不披露其个人信息。
- 在掘金或知乎补充「从反馈到改动」技术复盘；Bilibili/小红书可发布 30～60 秒前后对比，链接完整变更说明。
- 指标：关闭或明确回应 80% 的首批有效反馈；新增 1～3 名外部贡献者或文档改进提交；部署成功率较第 1 周提升。

### 第 4 周：沉淀案例与下一轮循环

目标是把短期发布转化为可持续维护的社区节奏。

- 征得作者明确同意后，整理 2～3 个真实部署案例：使用场景、部署环境、遇到的问题和最终方案。没有授权时仅做匿名统计。
- 发布「首月复盘」：展示目标与实际数据、最常见问题、下一月优先级，以及仍存在的限制（包括写接口的安全状态）。
- 更新路线图和贡献入口，邀请读者提交可复现 Issue、部署文档修正或使用案例；为高频问题补充 FAQ。
- 指标：形成至少 1 篇复盘、1 次文档更新和 1 个公开路线图；下月保留每周一次反馈整理、每两周一次版本说明的节奏。

## 反馈闭环与内容原则

1. 每条推广内容使用一致的反馈入口，并提示读者提交操作系统、Node 版本、部署平台、复现步骤和截图（注意打码）。
2. 每周固定一次整理反馈：确认、复现、标记优先级、回复预计处理方式；不能复现时请补充信息，不承诺无法保证的时间点。
3. 优先用真实数据与真实改动说明价值：例如「本周 12 人尝试部署，9 人成功，新增 2 条 FAQ」，不把浏览量等同于用户价值。
4. 严禁购买流量、刷 Star、刷评论、诱导点赞/收藏/关注，或使用夸大、虚假「零门槛」「绝对安全」等表述。内容标题应与实际能力、限制和维护成本一致。
5. 对安全、隐私和部署风险保持透明；在写接口完成鉴权前，将所有公网演示限定为不含写入能力的安全范围。

| 安全风险或待验证假设 |  |  |

若数据不达预期，先检查教程是否可复现、内容是否精准触达目标读者、反馈入口是否清楚；只根据证据调整选题和文档，不以制造噱头或不当互动来追逐增长。
